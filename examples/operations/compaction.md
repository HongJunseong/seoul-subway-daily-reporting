# 닫힌 시간의 작은 Delta 파일 실험

2026-10-11 별도 로컬 합성 lake에 5분 간격의 도착 snapshot 36개·각 1,000행을 저장했다. Spark 3.5.7 local[2]·Delta Spark 3.2.0이며 기존 수집·Silver·15분 Gold 코드를 사용했다. 실제 API 관측이나 운영 데이터는 아니다.

대상은 KST 2026-01-31 23:00~2026-02-01 00:00이다. 22시·다음 날짜 00시 파일은 유지했다. [실제 생성 증거](compaction.json)를 그대로 복사했다.

| 항목 | 유지보수 전 | 유지보수 후 |
|---|---|---|
| 전체 Bronze 행 | 36,000 | 36,000, 전체 컬럼 SHA-256 일치 |
| 전체 활성 파일 | 72 | 49 |
| 대상 시간 파일 | 24 | 1 |
| 대상 시간 파일 bytes | 1,532,105 | 1,174,152 |
| 인접 파티션 파일 | 48 | 48, path/size 해시 일치 |
| Bronze 버전 | 35 | 36, dataChange=false |
| 한 시간 조회 중앙값 | 0.661564초 | 0.172950초 |
| 마지막 15분 조회 중앙값 | 0.559446초 | 0.156256초 |

compaction 실행은 0.939750초, 입력 생성은 36.227858초, 전체 검증은 72.477143초다. 전체 검증에는 행 해시·Silver/Gold 처리·과거 버전 읽기·조회 표본·두 번째 유지보수가 포함된다. 초기 합성 입력 생성은 별도 Spark 회귀와 일부 겹쳤으며 조회 표본은 해당 회귀 종료 후 측정했다. 전체 시간은 격리된 처리량 측정으로 사용하지 않는다.

## 정확성과 재처리

전체 원본의 raw_payload·run_id·원천/관측 시각·record hash를 포함한 모든 컬럼의 해시가 같다. 유지보수 후 과거 버전 35의 전체 행도 다시 읽어 일치를 확인했다. 인접 시간대의 실제 활성 파일 path/size 해시가 그대로이며 유지보수 add/remove는 모두 dataChange=false다.

월말 자정의 00:00과 00:15 window를 기존 코드로 처리하고 다시 처리했다. Silver 24,000행과 15분 Gold 2,000행의 전체 컬럼 해시가 유지됐다. 원본 재처리 중에는 Bronze 버전 36이 그대로였다. 같은 대상의 두 번째 compaction은 파일 추가/제거 0이며 새 버전도 만들지 않았다.

회귀에서는 NULL ETA·중복 원본·마이크로초 snapshot을 가진 별도 Delta 테이블을 실제로 합치고 이전/이후 exceptAll 양방향과 인접 파일 보존을 확인했다. 이 입력을 정상 ETA Gold로 출판하는 테스트는 아니다.

## 조회와 판단

각 쿼리는 전후 버전을 고정해 한 번씩 warm-up한 뒤 다섯 쌍을 번갈아 실행했다. 전체 시간 조회는 12,000행, 마지막 15분은 3,000행이다. 행 수·ETA 정수 합·원문 문자 수가 같았으며 모든 시간 표본을 JSON에 보존했다.

파일 누적을 줄이는 방법과 로컬 조회 변화가 확인됐다. 운영 비용 절감률·SLA·대용량 성능은 검증하지 않았다. OS/JVM/metadata cache가 남고 candidate bytes는 실제 읽기 bytes나 S3 요청량이 아니다. 약 1MB의 출력도 여전히 작은 파일이므로 시간 파티션을 유지할지 바꿀지는 장기 입력 분포와 재처리 비용으로 결정한다.

자동 compaction 일정과 운영 S3 writer를 추가하지 않았다. VACUUM과 이전 파일 삭제도 수행하지 않았다. 운영 도입 전에는 수집 신선도·공유 writer pool 대기·유지보수 쓰기 비용·반복 조회의 읽기 비용을 함께 측정한다. [재현·선택 기준](../../docs/STORAGE_MAINTENANCE.md)에 절차를 기록했다.
